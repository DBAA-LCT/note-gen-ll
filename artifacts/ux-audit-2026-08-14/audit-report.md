# NoteGoal 非 AI 功能体验审计（2026-08-14）

## 审计范围

- 目标管理
- 日程
- 同步
- 手机端
- 本轮明确排除 AI 功能本身

证据来自当前安装版 NoteGoal 的桌面实机界面、当前代码库，以及本轮启动/静态检查。没有修改产品代码或用户数据。

## 总体结论

当前主要问题不是视觉精修不足，而是信息架构分散、失败状态不可见、同步概念混用，以及桌面逻辑直接复用到手机端。优先修复后，用户对“功能在哪、现在是否生效、失败后怎么办”的判断会明显改善。

## 流程步骤与健康度

### 1. 从笔记进入规划工作区 — 较差

可见证据：`01-current-desktop.png`、`02-today-desktop.png`。

- 规划入口分散在左侧栏动作、编辑器标签页、顶部独立日程按钮三处。
- 日程不属于“今日 / 目标 / 回顾”这一组，而是顶部单独按钮，用户难以形成统一心智模型。
- 顶部多个图标按钮在无障碍树中没有名称；读屏用户只能听到“按钮”。

### 2. 查看今日计划并开始执行 — 一般偏差

可见证据：`02-today-desktop.png`。

- 当前目标进度只有 3%，但当天没有任务，界面仍出现卡片内和页面顶部两个“开始执行”。两者是否进入同一模式并不清楚。
- “目标总览”是文字链接式动作，重要性弱于多个执行按钮，容易让用户先进入一个无任务的执行状态。
- 手机底部导航把该入口命名为“目标”，但打开后默认页面是“今日”，导航名称和落地内容不一致。

### 3. 创建、编辑和变更目标 — 较差

代码确认：

- `LearningApp` 和桌面 `LearningWorkspace` 都先判断 `!initialized` 并返回加载动画，错误提示写在后面的正常分支。初始化失败后会永久显示“正在准备规划空间…”，用户永远看不到实际错误。
- 目标状态更新没有 `try/catch`。网络、数据库或文件失败时，Promise 会被静默丢在事件处理器里，用户没有失败反馈。
- 手动创建目标时，只有 `planMarkdown` 已经有值才显示“总体规划”输入框；全新手动目标无法手工填写总体规划。
- 目标卡片的更多菜单按钮没有可访问名称。

### 4. 查看和编辑日程 — 较差

代码确认：

- 日程被实现为独立工作区；从规划工作区点击日程会先把活动视图重置为“今日”，再异步打开另一个标签。打开失败时用户会被送回今日且没有解释。
- 月视图数据 `reload()` 没有加载、错误或重试状态；读取失败会留下空白或旧数据。
- 保存、删除、拖动事件均缺少统一异常处理。失败时通常不会出现明确提示。
- 月历日期格的键盘 Enter/Space 只能展开日期；鼠标双击才能快速新建，键盘用户没有等价操作。
- 拖动日程没有键盘替代操作，也没有移动后的可访问状态播报。

### 5. 配置并理解同步 — 差

代码确认：

- 桌面同步页的左侧平台选择只是“正在查看的平台”，真正生效的是 `primaryBackupMethod`；界面没有把这两个概念清楚区分。
- 自动同步开关是否可用却按“正在查看的平台”计算，可能出现主同步平台正常、但因为用户浏览了一个未连接平台，自动同步选项被禁用的情况。
- 手机同步页反过来按“主同步平台”计算可用性，同时展示另一个正在查看的平台；桌面与手机的判断逻辑不一致。
- 手机同步页加载保存的 `cloudFolder` 时，在非 Android 环境会映射为 GitHub，并调用 `setPrimaryBackupMethod` 写回。打开设置页本身就可能改变主同步方式。
- 云文件夹连接测试捕获异常后只把状态改成失败，没有把失败原因呈现给用户。
- 所有平台在页面打开时同时检查，会增加等待和网络噪声；用户只需要先知道当前主平台是否健康。

### 6. 手机端整体体验 — 差

代码确认：

- 手机应用初始化是一条很长的串行链：设置、数据库、同步运行时、向量库、MCP 等。任一环节失败只写控制台，页面继续显示，造成部分功能悄悄失效。
- 手机规划只在顶部显示“今日 / 目标 / 回顾”，但代码仍包含日程和复习页面；它们只能从今日页内部绕行，发现成本高。
- 目标创建、目标规划和日程编辑继续使用居中的桌面对话框，而不是项目已有的响应式抽屉组件。窄屏键盘弹起时，保存按钮存在被遮挡的风险。
- 手机同步页一次堆叠平台连接、映射树、文件自动同步和三类数据同步，页面很长，缺少“连接成功 → 选择工作区 → 开启同步 → 验证结果”的任务分步。

## 最高优先级修复建议

1. 修复永久加载：错误状态必须优先于 `initialized` 判断，并提供“重试”。同样覆盖目标、日程和手机全局初始化。
2. 统一规划信息架构：把“今日、目标、日程、回顾”放在同一导航层；桌面与手机使用相同名称和落地页。
3. 重做同步状态模型：明确区分“主同步平台”和“正在配置的平台”；所有开关按主平台判断，并在界面持续显示当前主平台。
4. 给目标和日程所有异步写操作补齐 pending、成功、失败和重试；禁止用未处理 Promise 作为用户反馈。
5. 手机端把目标/日程表单切换到已有的响应式 Dialog/Drawer，并验证软键盘、320px 宽度、安全区和大字号。
6. 为目标、日程、同步至少补关键状态测试：初始化失败、保存失败、主平台切换、手机恢复已保存平台、空任务执行。

## 验证结果与限制

- 安装版 NoteGoal 可以启动并进入“今日计划”。
- 本地 Next 开发入口能监听端口，但首页和 `/core/main` 在 30 秒内均无响应；无法用浏览器完成窄屏截图。
- `pnpm lint` 和 `tsc --noEmit` 在本轮时限内均未完成且没有输出。
- 仓库仅发现 3 个测试文件，没有目标、日程或同步相关测试。
- 本轮未连接真实远端做写入、删除或冲突测试，以避免改动用户同步数据。
- 手机端没有取得 Android 实机截图，因此手机布局问题中标注的遮挡、软键盘和手势问题仍需设备验证。
- 截图只能支持可见层面的无障碍风险，不能证明完整 WCAG 合规性；键盘、读屏、缩放和动态状态播报仍需专项测试。
